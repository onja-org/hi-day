## Answers to the six survey questions (file references)

**1. Timer start/stop state** lives **server-side, authoritatively** (per `docs/adr/0006-time-entries-single-running-timer-server-authoritative.md`). The desktop app keeps only a client-side mirror, and that mirror lives in the **renderer**, not the main process: `runningEntry` (`desktop/src/renderer/renderer.ts:147`), set via `setRunning()` (`renderer.ts:193-205`). It's populated three ways: (a) the initial/periodic poll `refreshStatus()` → `GET /device/time-entries/current` every 15s (`renderer.ts:74,302-319`), (b) the Start/Stop/Switch button handlers calling `window.api.tracking.start/stop/switchTo` (`renderer.ts:330-375`), and (c) idle auto-stop/discard (`renderer.ts:247-257,381-394`). All of these go through preload's `window.api.tracking.*` (`desktop/src/preload/preload.ts:51-77`) to `ipcMain.handle('tracking:start'|'stop'|'switch'|'status', ...)` in `desktop/src/main/main.ts:113-145`, which just forwards to `ApiClient` (`desktop/src/main/api-client.ts`) — **the main process holds no timer state of its own**, it's a stateless IPC-to-HTTP relay. This matters for Stage A: the plan's architecture diagram puts "timer state" in the Electron main process alongside the session engine, but today that state exists only in the renderer, re-derived from the server. Whatever owns the session engine will need its own source of "is a timer running," most likely a main-process poll or a renderer→main IPC push, not a read of the renderer's variable.

**2. Foreground window/app detection: nothing exists.** No `get-windows`, no native module, no polling of the active window anywhere in `desktop/src/`. `desktop/README.md:6-7` confirms this explicitly: "activity capture (apps/windows, screenshots, activity level) isn't built yet." `docs/TECH_DESIGN.md:51,93` names `get-windows` as the intended library, but it's not in `desktop/package.json`'s dependencies and no code references it.

**3. Local persistence today: two flat files, no database.** `AuthStore` (`desktop/src/main/auth-store.ts`) writes/reads `session.dat` under Electron's `userData` dir, encrypted via `safeStorage` when available, falling back to plaintext (`auth-store.ts:26-49`, `README.md:127-130`). `getOrCreateDeviceFingerprint` (`desktop/src/main/device-identity.ts`) writes a plain-text `device-fingerprint.txt` the same way (`device-identity.ts:12-25`). **No SQLite, no `better-sqlite3` in `desktop/`'s own dependencies** — the one lockfile hit is an unused optional peer dep of the backend's TypeORM. **Sync to backend is synchronous and per-action, not batched**: every timer/project/task/idle-policy call goes straight through `ApiClient.deviceRequest` (`api-client.ts:172-206`) as an immediate `fetch`, and fails visibly on-screen if the backend is unreachable (`README.md:135-137`, "No offline queue... fail... if it's unreachable"). There is no queue, no retry, no idempotency key anywhere in the desktop app today.

**4. Main↔renderer communication** is a conventional `contextBridge` + `ipcMain.handle`/`ipcRenderer.invoke` request-response setup, nothing push-based from main to renderer. Preload (`desktop/src/preload/preload.ts`) exposes a typed `window.api` surface via `contextBridge.exposeInMainWorld('api', api)` (`preload.ts:83`); the `BrowserWindow` is created with `contextIsolation: true, nodeIntegration: false, sandbox: true` (`main.ts:43-48`). All nine channels (`auth:status/login/logout`, `tracking:listProjects/listTasks/start/switch/stop/status/idlePolicy`, `idle:seconds`) are registered in one place, `registerIpcHandlers()` (`main.ts:56-160`), and are all invoke/await request-response — **there is no `webContents.send`/`ipcRenderer.on` push channel anywhere**, so a main-process session engine that needs to tell the renderer something unprompted (e.g. a coverage/permission-state change) has no existing precedent to follow and will need to introduce one.

**5. `electron-builder` is configured** (`desktop/electron-builder.yml`), but it bundles **no native binaries and declares no `extraResources`** — `files` is just `dist/**/*` and `package.json` (`electron-builder.yml:11-13`). Targets are set up for all three OSes (NSIS/win, dmg+zip/mac, AppImage+deb/linux), `publish: null`, and macOS `identity: null` (unsigned, per `README.md:115-118`, "Known limitations"). Windows/macOS signing (mentioned as required in Stage C/G of the plan) has no infrastructure at all yet — no certs, no notarization credentials, nothing wired into `.github/workflows/desktop-build.yml`, which currently just runs `pnpm --filter desktop dist:{linux,win,mac}` unsigned on each OS runner.

**6. Test setup:** Vitest (`desktop/vitest.config.mts`), scoped to `src/main/tests/**/*.spec.ts` only (no renderer tests, no Electron-boot/integration tests). Three existing spec files are all narrow, pure-function unit tests with no OS mocking beyond a real temp dir: `api-base-url.spec.ts`, `device-identity.spec.ts` (uses `mkdtempSync`/`rmSync` against a real tmp directory, not a mock), and `platform.spec.ts`. This is a good structural match for the plan's Step 3 requirement (pure session engine, table-driven, zero OS mocks) — follow the same "one small pure module, one matching spec file" convention rather than introducing a different test style.

## Bottom line

Stage A is close to 100% new construction — nothing in `desktop/` today does subprocess
management, foreground-window detection, local durable storage, or batched/idempotent sync.
The two genuine extension points are `ApiClient`'s request/error conventions (for the sync
layer) and the existing pure-module-plus-spec-file pattern (`platform.ts`, `device-identity.ts`)
for the session engine and normalization pipeline. The one architectural change Stage A forces
that isn't called out in the plan: **timer running/not-running has to become main-process
state**, since today it only exists as a renderer-side mirror of the server.
