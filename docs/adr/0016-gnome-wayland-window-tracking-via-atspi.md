# GNOME Wayland window/app tracking via AT-SPI2, not a GNOME Shell extension

`docs/adr/0009-...` shipped window tracking knowing it had no Wayland support at all — `get-windows`, and later `@paymoapp/active-window` (`docs/adr/0011-...`), are X11-only on Linux "for security reasons." That ADR named the real fix ("a GNOME Shell or KDE-specific D-Bus extension") and deliberately deferred it as "a different, much larger, non-portable piece of work." This ADR is that follow-up, for GNOME specifically (the desktop environment actually in use on the machines that need this).

## The mechanism

This repo already has almost everything needed: the Linux URL-tracking resolver (`desktop/src/main/resolvers/linux/atspi.ts`) solves a nearly identical problem — getting the focused window's app name and title on GNOME, on both X11 and Wayland — via **AT-SPI2 over D-Bus** (`dbus-next`, already a direct dependency), not a GNOME Shell extension. `AtspiClient` subscribes to the accessibility bus's `window:activate` signal and reads back `{ appName, title }` on every activation. `gnome-window-focus-tracker.ts` (new) reuses this class as-is, just for a different consumer than the URL resolver.

The one piece `AtspiClient` doesn't already do, and the one open question this ADR had to resolve empirically rather than by inspection: **ordinary, already-running applications only start emitting `window:activate` once `org.a11y.Status.IsEnabled` is set `true`** — a distinct, session-wide D-Bus property (on the regular session bus's `org.a11y.Bus` object, *not* the accessibility bus itself — an easy mistake, since it looks like it should live there) from the per-application accessibility-tree richness `resolvers/linux/browser-activation.ts` already manages for browsers specifically (that trick forces one process's *own* tree depth via a `.desktop`-launcher rewrite at spawn time, needed for reading a browser's address bar; it says nothing about whether that process, or any other, ever emits window-level focus events at all).

Verified live against a real GNOME Wayland session (`ubuntu:GNOME`, GNOME Shell), with zero relaunching of anything:
- 23 ordinary applications (terminal, Chrome, Slack, VS Code, Nautilus, VLC, gnome-shell itself, …) already carry minimal AT-SPI registration with no special setup.
- With `IsEnabled` at its default `false`, two clean 30-second listens for `window:activate` while switching focus produced **zero** events.
- With `IsEnabled` set `true`, the very next focus switch — on the same already-running, unmodified applications — produced `window:activate` events immediately, each carrying the correct `appName`/`title`.

## What this ADR decided

- **Set `org.a11y.Status.IsEnabled = true` once, at desktop-agent startup, session-wide** (`GnomeWindowFocusTracker.start()`), rather than attempting per-application launcher rewrites (which would need generalizing `browser-activation.ts`'s trick to every application on the machine — much bigger, and still misses anything not launched via a `.desktop` entry).
- **Never set it back to `false`.** Another AT-SPI consumer on the same session — a real screen reader, or this app's own URL-tracking resolver — may depend on it staying on, and there's no reliable way to tell whether this tracker was the one that turned it on. This is a real, user-visible side effect: GNOME's own Accessibility quick-setting will show as on for as long as the desktop agent has run at least once in that session. Accepted as the cost of the fix — the alternative (turning it off again) risks silently breaking a genuine assistive-technology user sharing the same session.
- **Feed this into `WindowSampler` as an additional data source for the Linux+Wayland branch only** (`window-sampler.ts`'s `tick()`), not a wholesale replacement of `@paymoapp/active-window` on X11 — X11 already works via the existing native module, and widening scope there wasn't needed to close this gap. AT-SPI could plausibly also help X11 in the future (it works on both), but that's out of scope here.
- **A missing/failed accessibility bus is a soft failure, not a startup error.** `GnomeWindowFocusTracker.start()` catches everything (missing `at-spi2-core`, the bus unreachable, whatever) and simply leaves `getLastFocus()` returning `null` forever — `WindowSampler` already treats that identically to today's pre-fix behavior (`'not-exposed'`), so a machine without a working accessibility bus degrades to exactly what it did before this ADR, never a crash.
- **No sample at all until the first real activation.** Right after startup, before the person has switched windows even once, there is nothing to report yet — `WindowSampler` falls back to `'not-exposed'` for that narrow window rather than fabricating a value.

## Known limitations

- Coverage depends on whichever applications actually emit `window:activate` once `IsEnabled` is on — verified for GTK/Electron/Chromium-family apps and GNOME Shell itself; an application that opts out of accessibility entirely would still report nothing, same as today.
- This is GNOME-specific in practice, even though nothing in the code hard-codes a GNOME check: `IsEnabled`/AT-SPI is a freedesktop-wide standard, but `window:activate` needs the compositor and toolkits involved to actually wire it up, which this ADR only verified for GNOME/Mutter. Other Wayland compositors (KDE/KWin, wlroots-based ones) were not tested and may or may not behave the same way — `support-gate.ts`'s own `evaluateSupport()` already only claims GNOME-on-Wayland support for the same underlying mechanism, for the URL-tracking feature.
