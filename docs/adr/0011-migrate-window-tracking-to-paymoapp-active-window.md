# Window tracking migrates from `get-windows` to `@paymoapp/active-window` — dropping the ESM-interop workaround and fixing the macOS title-reading gap `docs/adr/0009-...` had deliberately accepted

Requested as a refactor: replace `get-windows` (`docs/adr/0009-...`) with `@paymoapp/active-window` as the desktop agent's window-capture library. `WindowSampler` (`desktop/src/main/window-sampler.ts`) is the only place that talks to it; `classifyTitleUnavailability` (`desktop/src/main/window-sample.ts`) is the only place that reasons about *why* a title came back unavailable. Both changed; the surrounding architecture (`CaptureSettingsGate`, `TimerStatusGate`, `AppEventUploader`, the `windowTrackingEnabled`/timer-running gating) did not.

## What changed and why

- **No more ESM-interop workaround.** `get-windows` was ESM-only with no CJS build, forcing the `new Function('specifier', 'return import(specifier)')` dance documented in `0009-...` to dodge `ERR_REQUIRE_ESM` under this app's `module: "commonjs"` tsconfig. `@paymoapp/active-window` is published as a genuine dual ESM/CJS package (`package.json`'s `exports` map has a `require` condition pointing at a real `dist/index.cjs`), so a plain static `import` — downleveled by `tsc` to a plain `require()` — just works. `window-sampler.ts` lost the whole `dynamicImport`/`activeWindowPromise` machinery as a result.

- **Synchronous API, and a different "nothing to report" shape.** `get-windows`' `activeWindow()` was async and resolved `undefined` when there was no focused window. `@paymoapp/active-window`'s `getActiveWindow()` is synchronous and *throws* in that case instead. `WindowSampler.tick()` still catches and normalizes both into "no result for this tick" (a sample is still always emitted — same invariant as before), but `tick()` itself is no longer `async` — there's no actual async work left anywhere in the call path, `@typescript-eslint/require-await` caught this immediately.

- **One-time `initialize()` call.** `@paymoapp/active-window` requires calling `ActiveWindow.initialize()` once before any `getActiveWindow()`, regardless of platform. Electron's main process already has a running event loop by the time this is ever called (a `BrowserWindow` is open), so the default (`osxRunLoop` left unset) is correct — no manual run-loop pumping needed. Lazily called once, module-scope, mirroring the same the-real-default-is-a-lazy-singleton shape `loadActiveWindow` used before.

- **The macOS permission model changed, and this incidentally fixes `0009-...`'s accepted gap.** `get-windows` exposed `accessibilityPermission`/`screenRecordingPermission` flags to `activeWindow()`, and this app (per the original ticket's explicit choice) checked/prompted for Accessibility while passing `screenRecordingPermission: false` — but `get-windows`' own docs say `title` is actually gated by Screen Recording, not Accessibility, so window titles most likely never populated on macOS regardless of grant. `@paymoapp/active-window` doesn't expose an Accessibility concept at all; its only permission surface is `requestPermissions()`, which checks/requests **Screen Recording** — the permission that genuinely gates window titles on macOS. There is no coherent way to "just swap the library" while keeping the Accessibility-branded UI/IPC surface, since there is no Accessibility check left to show. So this migration renames the concept throughout, not just the library call:
  - `TitleUnavailabilityInput.macAccessibilityGranted` → `macScreenRecordingGranted` (`window-sample.ts`)
  - `CapturePermissionStatus.accessibilityGranted` → `screenRecordingGranted` (`main.ts`, `preload.ts`, `renderer.ts`)
  - IPC channels `tracking:requestAccessibilityAccess` → `tracking:requestScreenRecordingAccess`, `tracking:openAccessibilitySettings` → `tracking:openScreenRecordingSettings` (now opens System Settings' `Privacy_ScreenCapture` pane, not `Privacy_Accessibility`)
  - The renderer's banner copy, element IDs (`accessibility-banner` → `screen-recording-banner`, etc.), and CSS selectors.

  The non-prompting status check (used for the 30s poll and the initial banner render) deliberately still uses Electron's own `systemPreferences.getMediaAccessStatus('screen')` rather than `@paymoapp/active-window`'s `requestPermissions()` — the same reasoning `0009-...` already established for Accessibility applies unchanged to Screen Recording: macOS only shows its native grant prompt once, so calling the request-and-prompt function from a background poll (rather than an explicit "Grant Access" click) risks firing that one-time prompt at a moment the person never asked for it. `requestPermissions()` is only ever called from the `tracking:requestScreenRecordingAccess` handler, which only the renderer's "Grant Access" button click invokes — mirroring exactly how `systemPreferences.isTrustedAccessibilityClient(true)` was gated before.

- **Wayland gap unchanged.** `@paymoapp/active-window` only supports X11 on Linux ("For Linux, only the X11 windowing system is supported" — its own docs), same as `get-windows`. `platform.ts`'s `isWaylandSession()` check, and the short-circuit in `WindowSampler.tick()` that never even calls into the library under Wayland, needed no logic changes — only comment updates.

## Packaging: a second real bug found by actually verifying, not just assumed

Following the same verification bar `0009-...` set (build the Linux target, unpack the asar, execute the library's real call from the packaged output — not just trust source-mode success): `asarUnpack` was retargeted to `node_modules/@paymoapp/active-window/**/*` (a native `.node` addon still can't load from inside an asar). Initially that was assumed sufficient, since `@paymoapp/active-window` ships prebuilt binaries via `prebuildify`/`node-gyp-build` and (unlike `get-windows`) has no platform-conditional `optionalDependencies` to trip electron-builder's default `optionalDependencies`-dropping behavior.

That assumption was wrong. The first packaged build failed at runtime with `Cannot find module 'node-gyp-build'` — `@paymoapp/active-window`'s own (regular, non-optional) runtime dependency, the thing that actually locates and `require()`s the correct platform prebuild. electron-builder's dependency walker didn't pull it into the packaged `node_modules` under this repo's pnpm-workspace layout, even though it correctly included `@paymoapp/active-window` itself. Root cause not fully diagnosed (plausibly electron-builder's collector not fully following pnpm's `.pnpm`-symlinked node_modules structure for a dependency of a dependency), but the fix is the same shape as `get-windows`' `@mapbox/node-pre-gyp` issue before it: **`node-gyp-build` is now a direct dependency of `desktop/package.json`**, even though nothing in this app's own code imports it. Re-verified after the fix: unpacked the rebuilt asar and called `getActiveWindow()` directly from `release/linux-unpacked/resources/app.asar.unpacked` — it now resolves and runs.

## Consequences

- `classifyTitleUnavailability` now implements the *correct* model (Screen Recording gates title on macOS) rather than `0009-...`'s ticket-specified-but-wrong one. A future macOS-hardware verification pass should still confirm this live — nobody on this project has a Mac — but the mechanism now matches both libraries' own documented behavior, not just one.
- `docs/adr/0009-...` is marked `superseded-in-part`: its capture-library choice and macOS gap are superseded by this document; its `windowTrackingEnabled` setting design, the `CaptureSettingsGate`/`TimerStatusGate` polling architecture, and the Wayland gap all still stand unchanged.
- `desktop/README.md`, `docs/TECH_DESIGN.md`, and `docs/CAPABILITIES_FAQ.md` were updated to name `@paymoapp/active-window` instead of `get-windows`.
