# Window tracking uses `get-windows` (not `active-win`), gated by a new `windowTrackingEnabled` Organisation setting — with known, deliberately-shipped gaps on macOS title reading and Wayland app-name reading

Active window tracking (`docs/TECH_DESIGN.md` §5's first "Capture" module: apps/windows) needed both a capture library and an on/off settings module — neither existed yet. This ADR records three decisions and two accepted gaps that a future reader would otherwise have to rediscover.

## Considered options

- **`active-win` vs. `get-windows`.** The originating ticket named `active-win`. That package is deprecated on npm and renamed to `get-windows` (same author, sindresorhus) — `docs/TECH_DESIGN.md` §5/§10 and `docs/CAPABILITIES_FAQ.md` already name `get-windows` specifically, so this wasn't really a live choice. Using `get-windows@^9`.

- **Loading an ESM-only package from a CommonJS main process.** `get-windows`'s `package.json` declares `"type": "module"` with no CJS build — but `desktop/tsconfig.json` compiles the main process to `module: "commonjs"`. A literal `await import('get-windows')` gets downleveled by `tsc` into `require('get-windows')` (confirmed by compiling it against this repo's exact tsconfig), which throws `ERR_REQUIRE_ESM` against an ESM-only package. Fixed by hiding the specifier from `tsc`'s static rewriter: `new Function('specifier', 'return import(specifier)')`, typed via a local `Importer` alias, isolated to `desktop/src/main/window-sampler.ts`. This compiles to a genuine runtime `import()`, which Node has supported from CommonJS since Node 12 — verified end-to-end against a real packaged build (see the packaging section below), not just compiled in isolation. `desktop/eslint.config.mjs` flags this via `@typescript-eslint/no-implied-eval`; suppressed inline with a comment, since the specifier is a fixed internal string literal, never user input.

- **The on/off setting: a new entity/migration vs. reusing `Organisation.settings`.** Followed the exact precedent `docs/adr/0007-...` set for idle policy: a new typed field (`windowTrackingEnabled: boolean`) inside the existing `settings` jsonb column, not a new column or entity. `GET /device/capture-settings` mirrors `GET /device/idle-policy` one-for-one. Default is `false` for any org that hasn't explicitly set it (including orgs created before this shipped) — nothing is captured until an admin opts in, matching PRD FR-9's framing ("before capture begins, admins choose what is collected").

- **How the desktop agent learns about a setting change.** There's no push/websocket channel from the backend to the desktop main process. `CaptureSettingsGate` polls `/device/capture-settings` every 30s and also re-polls immediately on login/logout, starting/stopping `WindowSampler` only on an actual on/off transition (not every poll). A `webContents.send`-based push channel was considered and rejected for this pass — `main.ts` today only ever uses `ipcMain.handle` request/response, and a new push architecture isn't justified by this one narrow need.

- **Sampling requires a running timer, not just the org setting.** The ticket's own text didn't specify this, and the first implementation ran the sampler whenever logged in with the setting on, regardless of timer state — but Hubstaff (this product's own model) ties activity capture to being clocked in, and manual testing surfaced the gap before it shipped. Added `TimerStatusGate` (`desktop/src/main/timer-status-gate.ts`), structurally identical to `CaptureSettingsGate` but polling `GET /device/time-entries/current` (already used elsewhere for timer sync) every 15s — independently, since a running timer is server-authoritative and can change from the web console or another device (`docs/adr/0006-...`), not just this app's own Start/Stop/switch buttons. `main.ts` combines both signals with a plain `windowTrackingEnabled && timerRunning` check, recomputed whenever either gate reports a transition; the local `tracking:start`/`tracking:switch`/`tracking:stop` IPC handlers also trigger an immediate `timerStatusGate.pollOnce()` after their own network call resolves, so this app's own timer actions reflect instantly rather than waiting up to 15s.

## The accepted gap: macOS title reading is likely broken by design, on purpose, for this pass

`get-windows`'s own docs state that on macOS, `screenRecordingPermission: false` forces `title` to always come back as an empty string — **`title` is actually gated by the Screen Recording permission, not Accessibility** (this matches real Catalina+ macOS behavior: `CGWindowListCopyWindowInfo` redacts window titles without Screen Recording access). `accessibilityPermission` only gates the browser-tab `url` field, which this ticket doesn't use at all.

The ticket's own spec calls for `systemPreferences.isTrustedAccessibilityClient` (an Accessibility check) and `screenRecordingPermission: false` (deliberately, to avoid pre-empting the heavier Screen Recording prompt ahead of a future screenshot feature). Implemented exactly as specified — app name always works; on macOS, window title will most likely never populate, regardless of Accessibility grant. This was confirmed with the user as an explicit, accepted trade-off rather than silently patched over, because nobody on this project currently has macOS hardware to verify it live (same footing as `docs/adr/0007-...`'s unverifiable-on-this-dev-box idle-detection finding).

**If this needs fixing in a follow-up**: gate on `systemPreferences.getMediaAccessStatus('screen')` instead, pass `screenRecordingPermission: true` / `accessibilityPermission: false` to `activeWindow`, and change the banner to prompt for Screen Recording (no programmatic prompt exists for it — only `shell.openExternal` to System Settings' Screen Recording pane, and macOS typically requires relaunching the app after granting it).

## A second accepted gap: Wayland gives no app name either, not just no title — confirmed live, not just theoretical

The ticket's acceptance criteria state that Wayland (like an app that hides its title) should "still record the app name" and only mark the title unavailable. Implemented that way initially — but `get-windows`'s own docs say Wayland is unsupported *entirely*, "for security reasons," with no partial/app-name-only API. This was borne out on real hardware during manual verification (a real Ubuntu/Wayland desktop, not this project's headless dev container): every sample came back `{ appName: null, title: null, titleUnavailableReason: 'not-exposed' }`, sampling correctly every 5s, never skipping a tick — but with no app name at all, not just no title.

There's no fix available through `get-windows` — getting even just the focused app's name under Wayland would require a compositor-specific mechanism (e.g. a GNOME Shell or KDE-specific D-Bus extension), which is a different, much larger, non-portable piece of work, not a small follow-up. Accepted as a known gap on the same footing as this app's existing Linux idle-detection caveat (`docs/adr/0007-...`) rather than pursued further in this pass. The renderer's Wayland notice and `desktop/README.md`'s "Known limitations" were corrected to describe this accurately (no app name, not just no title) rather than restate the ticket's unachievable assumption.

## Consequences

- `classifyTitleUnavailability` (`desktop/src/main/window-sample.ts`) implements the ticket's stated model (Accessibility-first) rather than the corrected one — a future macOS-hardware verification pass should treat "does title ever actually populate" as an open question, not an assumption.
- A second, unrelated packaging bug was found and fixed while verifying this end-to-end: `get-windows`'s `index.js` unconditionally statically imports all three platform modules (macOS/Linux/Windows) due to ESM's eager static-import evaluation — even on Linux, loading it evaluates `lib/windows.js`, which imports the *optional* dependency `@mapbox/node-pre-gyp`. electron-builder's default packaging drops `optionalDependencies`, so a packaged build silently failed to load `get-windows` at all (`Cannot find package '@mapbox/node-pre-gyp'`) despite working fine in `pnpm dev`. Fixed by adding `@mapbox/node-pre-gyp` as a direct (non-optional) dependency of `desktop/package.json` — verified by building the Linux target, unpacking the asar, and executing `get-windows`'s `activeWindow()` directly from the packaged output. `asarUnpack: ['node_modules/get-windows/**/*']` was also added, since the native `.node` addon can't load from inside an asar archive.
