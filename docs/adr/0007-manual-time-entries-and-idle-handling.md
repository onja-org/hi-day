# Manual time entries and idle-discard both need client-supplied timestamps — amends ADR-0006; edits are your-own-entries-only; idle policy lives on Organisation.settings

Adds the epic's remaining two Time Tracking sub-tasks: manual time entry/editing with an audit trail, and idle detection/handling. Both push on a claim ADR-0006 made explicitly ("timestamps are server-assigned only... no client-supplied `startedAt`") — this ADR amends that claim rather than leaving the code and the record disagreeing.

## Considered options

- **Keep `start`/`switch`/`stop` fully server-authoritative and add manual entry as a wholly separate code path.** Rejected as unnecessary duplication. Instead, exactly three call sites now accept a client-supplied timestamp — `createManual` (both `startedAt` and `endedAt`), `update` (either), and `stop` (an optional `endedAt`, used only for backdating an idle-discard) — and all three run through one shared validator (`assertValidRange`: end after start, end not in the future). `start`/`switch` themselves are untouched: a *live* timer's `startedAt` is still always `new Date()`, never client input. The distinction that matters isn't "manual vs. agent" — it's "logging something that already happened" vs. "beginning to track something now."
- **Who can edit a Time entry.** Initially scoped this to "the caller's own entries only" (see this ADR's original text, superseded here), reasoning that there was no way to even *list* another Membership's entries yet, so building edit access for a view that didn't exist would be speculative. Revised after explicit product direction: **only an org admin or manager can edit a Time entry at all — a plain member/finance can't edit any entry, not even their own — and a manager specifically cannot edit their *own* entries** (only an admin can). This is a deliberate segregation-of-duties control: the role trusted to correct everyone else's hours shouldn't also be able to quietly adjust its own without anyone else's involvement; admin, as the top role, has no one to segregate from. This made "list another Membership's timesheet" a real requirement rather than a speculative one, so `TimeEntriesService.list` now accepts an optional `targetMembershipId` (admin/manager only; a plain member/finance passing anyone but their own 403s), and each `TimeEntryListItem` carries a computed `canEdit` so the frontend never has to re-derive the rule. Manual entry (`createManual`) keeps the old, looser rule (org admin/manager, or a ProjectMembership on the project) unchanged — logging your own retroactive time is self-service; editing already-recorded hours (yours or anyone else's) is the part that needed gating.
- **Reject edits to a still-running entry, rather than allowing `endedAt` to be set through `update`.** A running entry has no `endedAt`; letting `update` set one would silently stop a timer without ever emitting `time_entry.stopped`, and letting `update` change `projectId` on a live entry has no clean "when did the attribution change" boundary. `update` 409s on a running entry and points the caller at `stop`/`switch` instead.
- **Org idle policy: build a proper settings entity, vs. add two typed keys to `Organisation.settings` (already `jsonb`, already used this way for `address`/`website`).** Went with the existing jsonb column — it's already the established pattern (`OrganisationsService.updateProfile`/`toProfile`), so this isn't introducing a new mechanism, just its first *typed* use (`idleHandling: 'off' | 'flag' | 'auto_subtract'`, `idleThresholdMinutes: number`, both optional with defaults `'flag'`/`5` applied on read — see `organisations/idle-policy.ts`). A dedicated entity would be premature for two fields with no independent lifecycle from the Organisation row itself.
- **Idle handling default: `flag` (prompt the person to keep/discard) vs. `auto_subtract` (silently end the timer).** Chose `flag` as the default an org has to explicitly opt out of. The epic's own risk notes name the exact failure mode `auto_subtract` risks ("watching a video is not idle work") — silently cutting real tracked time on a false positive, with no way for the person to know it happened, cuts hardest against a product positioned as transparent and trust-first. `auto_subtract` is fully supported (an org can choose it), it's just not what a newly-created org gets by default.
- **Idle detection mechanism: Electron's `powerMonitor.getSystemIdleTime()`**, per `docs/TECH_DESIGN.md`. Confirmed working in principle but **verified non-functional on this dev machine** — it stayed at `0` across a 10s sit-still test, because this machine runs Wayland and Electron's Linux idle time goes through the X11 XScreenSaver extension, which Wayland sessions generally don't back. The desktop `README.md`'s existing "Linux best-effort" framing already covers this; idle detection is real, shipped code (works on Windows/macOS and X11 Linux) but its live behavior could not be manually verified in this environment — only the surrounding plumbing (IPC wiring, policy fetch, prompt UI, the backdated-stop call) was.

## Consequences

Audit metadata for the three new/changed actions shares one shape rather than three ad-hoc ones: `time_entry.created_manually` and `time_entry.updated` carry `{ timeEntryId, ...fields }` / `{ timeEntryId, changed: { field: { from, to } } }` respectively, and a backdated `time_entry.stopped` adds `{ reason: 'idle', discardedSeconds }` on top of its normal `{ timeEntryId }`. `update` only writes an audit entry when something actually changed (a same-value "edit" is a no-op, not a logged event).

`TimeEntrySource` gained a third value, `'manual'`, via `ALTER TYPE ... ADD VALUE` (hand-written migration, run against the dev DB directly — same reasoning as ADR-0006's partial-index migration: `migration:generate` isn't trusted for anything beyond a plain column diff). Postgres has no `DROP VALUE`, so removing it would mean recreating the enum type entirely — the migration's `down()` is deliberately a no-op, accepted as a one-way migration.

Not built in this pass: a manager/admin timesheet-review view (still FR-27, still deferred), overlapping-entry validation (not in the epic's acceptance criteria, and genuinely ambiguous for a *running* entry's open-ended range — left for a future decision if asked for), and manual time entry from the desktop agent (kept web-only; the agent's 420×560 window is the wrong surface for a multi-field form, and nothing about "web console... manual timers & entry" in the release plan's Phase 1 suggests otherwise).
