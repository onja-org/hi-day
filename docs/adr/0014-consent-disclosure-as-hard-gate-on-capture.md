# Consent & disclosure as a hard, backend-enforced gate on capture

Window tracking, screenshots, and activity sampling shipped before any consent mechanism existed — this closes that gap for a compliance-critical requirement ("no capture feature should go live before this is in place").

We modeled disclosure text as its own versioned entity (`DisclosureVersion`), not another toggle in `Organisation.settings`: unlike `idleHandling`/`windowTrackingEnabled`, this needs an audit trail — a `ConsentRecord` must keep pointing at exactly the text a person agreed to, even after an admin later edits it. Consent is recorded per-Device, not per-Membership, since capture happens locally on a specific machine and a second device someone pairs later hasn't been told anything about itself yet.

Disclosure text can vary by jurisdiction, so each `DisclosureVersion` carries an optional `Membership.disclosureRegion`-matched region. This is deliberately named `disclosureRegion`, not `region` — `Organisation` already has an unrelated `region` column (`OrganisationRegion`, an infrastructure/data-residency placeholder, currently always `'us'`); reusing "region" for a per-Membership legal jurisdiction would have collided with that existing, differently-scoped term.

For a capture-enabled org, declining is a hard stop: the Device can't be used at all (no login, no timer) until consent is given. We considered a soft decline (capture stays off, everything else keeps working), but that produces inconsistent, gap-riddled capture records across a team and quietly undermines the org's own tracking policy — worse for compliance than forcing the choice up front. This means what's recorded is better described as an acknowledgment gating continued device use than consent in the "freely given, no consequence" sense — see `CONTEXT.md`'s Consent record entry.

The gate is enforced backend-side (`POST /device/app-events`, `POST /device/activity-samples`, the screenshot presign endpoint all reject a Device with no valid `ConsentRecord` for the org's current `DisclosureVersion`), not just in the Electron client — a compliance guarantee that only a trusted client honors isn't actually a guarantee. The desktop app's own consent screen is a UX nicety on top of this, not the enforcement mechanism itself. One known gap: a presigned screenshot-upload URL issued *before* consent went stale (a new `DisclosureVersion` published, or consent revoked) stays valid for its own TTL — rejecting the presign *request* blocks new captures, but doesn't invalidate a URL already handed out. Accepted as a narrow, short-lived window rather than closed with URL revocation, which Wasabi's presigned-URL model doesn't support cheaply.

On a 403-no-consent response from any of these endpoints, the agent discards the queued batch rather than retrying it (the offline queue's exponential-backoff retry is for transient failures, not a rejection that will never resolve itself) and stops the capture loop client-side rather than continuing to capture-but-fail-to-upload.
