# Desktop-facing controllers keep their raw response shape — the message/toast reshape (docs/adr/0018, docs/adr/0019) never touches them

`frontend/src/lib/*.ts` calls the web-facing controllers (e.g. `time-entries.controller.ts`); the desktop Electron app calls a separate set of controllers (`device-tracking.controller.ts`, `device-pairing.controller.ts`) sitting on top of the *same* services (e.g. `TimeEntriesService`). Desktop's `api-client.ts` casts every response body straight to its expected TypeScript type with no runtime validation and no type shared with the backend (confirmed: nothing under `desktop/src` imports from `backend`, and the same shapes are hand-duplicated across `api-client.ts`, `preload.ts`, and `window.d.ts`). Changing a shared response shape from a raw entity (e.g. `TimeEntrySummary`) to `{ timeEntry, message }` would not throw or fail to compile on the desktop side — it would silently produce `undefined` field reads at six call sites in `renderer.ts` (`setRunning(result.data)` after start/switch/stop/pause/resume), degrading the running-timer UI without any visible error.

Decision: the message/toast reshape (docs/adr/0018, docs/adr/0019) is scoped strictly to endpoints the Next.js frontend actually calls. `device-tracking.controller.ts` and `device-session.controller.ts` are desktop-only in full and are left untouched — `device-session.controller.ts`'s two methods (`heartbeat`, `logout`) are guarded by `DeviceSessionGuard` (bearer device-token auth, not the web's cookie/JWT auth), already return `void`, and have zero callers anywhere in `frontend/src` (confirmed by grep) — only `desktop/src/main/api-client.ts` calls them. `device-pairing.controller.ts` is **not** a clean file-level exclusion, though: it mixes desktop-facing methods (`POST /device-pairing` start, `GET :code/status` poll — both called only by `desktop/src/main/api-client.ts`) with one web-facing mutation, `POST /device-pairing/:code/approve` (called by `frontend/src/lib/approveDevicePairing.ts`, when an authenticated web user approves a pairing request). Only `approve` is in scope for the message reshape; `start`/`status` keep their raw shape exactly as before, same as `device-tracking.controller.ts`. `GET /device/time-entries/current` was already the one exception returning an envelope (`{ entry, now }`) before this change, and needed no adjustment either way.

This is only safe because error-message normalization (joining a validation error's `string[]` into one toastable string) lives entirely in a new frontend-only utility (`frontend/src/lib/parseApiError.ts`) — nothing on the backend's thrown-exception payloads changed. In particular, `TimeEntriesService`'s `ConflictException({ message, runningEntry })` (thrown from the same service both the web and desktop controllers sit on) is untouched; desktop's `pollPairing`/`deviceRequest` error parsing (`ErrorResponseBody`, expecting `{ message, runningEntry }` as raw fields) still gets exactly the shape it always has.

## Consequences

Web and desktop now have (further) diverging response shapes for logically-the-same operations (start/stop/pause/resume a timer) even though they share a service layer. A future change to `TimeEntriesService`'s thrown exceptions or to `time-entries.controller.ts`'s return shape must not be assumed to be safe for `device-tracking.controller.ts` just because they share a service — re-run the same blast-radius check (grep desktop's `api-client.ts`/`renderer.ts` for the affected fields) before touching either controller's response shape again. If desktop ever needs the same message/toast treatment, that's a separate, explicit change to `api-client.ts`, `preload.ts`, `window.d.ts`, and the `renderer.ts` consumers listed above — not a side effect of a web-side change.
