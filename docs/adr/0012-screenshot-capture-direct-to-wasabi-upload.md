# Screenshot capture uploads directly to Wasabi via presigned URLs, gated by a new `screenshotsEnabled`/frequency/retention Organisation setting, with an hourly retention-cleanup cron

Screenshot capture (`docs/TECH_DESIGN.md` §5's second "Capture" module, PRD FR-16) needed a capture library, a direct-to-storage upload path, a retention-cleanup job, and a settings surface — none of which existed yet. This ADR records the decisions a future reader would otherwise have to rediscover.

## Considered options

- **Object storage: Wasabi, not Cloudflare R2.** Wasabi was the intended provider from the start — `docs/TECH_DESIGN.md` §2/§6/§10 previously named Cloudflare R2, a leftover from an earlier draft that was never updated once Wasabi was actually chosen and provisioned; corrected as part of this pass. `backend/.env` (this project's actual local dev config) already carried real `WASABI_*` credentials and a `WASABI_BUCKET=workforce-monitoring-screenshots` — plus a `SCREENSHOT_URL_TTL_SECONDS` var — clearly provisioned for this exact feature, confirming Wasabi as ground truth. Built against it via `@aws-sdk/client-s3`/`@aws-sdk/s3-request-presigner` (`forcePathStyle: true`, since Wasabi serves buckets at `<endpoint>/<bucket>/<key>` rather than AWS's virtual-hosted `<bucket>.<endpoint>` style).

- **Direct-to-storage upload shape: presigned PUT + a separate metadata POST, not a proxy through the API.** Matches `docs/TECH_DESIGN.md` §1/§4 exactly ("the agent requests a presigned URL and uploads the image straight to Wasabi; only the metadata ... goes to the API"). Two new `/device` routes: `POST /device/screenshots/upload-url` (agent sends `capturedAt`, gets back `{ uploadUrl, storageKey }`) and `POST /device/screenshots` (agent sends `{ storageKey, capturedAt }` *after* the PUT to Wasabi succeeds, to record the metadata row). The storage key is always server-generated (`ScreenshotStorageService.buildStorageKey`, namespaced `screenshots/<organisationId>/<deviceId>/<epochMs>-<uuid>.jpg`), never client-supplied — `ScreenshotsService.recordScreenshot` additionally checks the key the agent posts back actually starts with `screenshots/<organisationId>/<deviceId>/`, so one device in an org can't misattribute a screenshot under another device's key even if it tried to record an arbitrary key.

- **The on/off + frequency + retention setting: extending `CaptureSettings` (the existing `windowTrackingEnabled` jsonb-backed mechanism) rather than a new settings module.** Same precedent as `docs/adr/0009-...`/`docs/adr/0007-...`: `screenshotsEnabled` (boolean, default `false`), `screenshotFrequencySeconds` (default 600 — 10 min), `screenshotRetentionDays` (default 30) all live in `Organisation.settings` alongside `windowTrackingEnabled`/`idleHandling`. `GET /device/capture-settings` already returned the whole `CaptureSettings` object (the desktop agent's `CaptureSettingsGate` was already polling and diffing the full object, not just the one boolean it used) — so no new device endpoint was needed, just new fields on the existing one and a corresponding generalization of `CaptureSettingsGate`'s `onChange` callback (was `(enabled: boolean)`, now `(settings: CaptureSettings)`) so the agent can react to frequency changes too, not just on/off. Screenshot capture, like window tracking, only runs while a Time entry is also running (Hubstaff-style — same `TimerStatusGate` combination `main.ts` already used for window tracking).

- **`keptUntil` computed at capture time, not re-derived per cleanup run.** `docs/TECH_DESIGN.md` §3's schema explicitly lists `kept_until` as a `screenshot` column. Implemented as `capturedAt + screenshotRetentionDays (at that moment)`, stored once on insert (`Screenshot.keptUntil`) rather than joining `organisations.settings` on every cleanup pass. Consequence, called out on the entity and worth restating here: **lowering an org's retention is not retroactive** — it only shortens the lifetime of screenshots captured *after* the change; existing rows keep the `keptUntil` they were given at capture time. This trades a small amount of "your new setting didn't delete anything yet" surprise for a cleanup query that's a single indexed scan (`WHERE keptUntil < now()`) rather than a join across every org's current setting — consistent with `docs/TECH_DESIGN.md` §8's "shaped by design, not by horsepower" scaling goal. If this surprises admins in practice, a follow-up could re-derive `keptUntil` for existing rows when retention is shortened; not done here.

- **Retention cleanup: `@nestjs/schedule`'s `@Cron`, hourly, not a separate worker/queue.** `docs/TECH_DESIGN.md` §2/§4 describes a BullMQ+Redis job queue for "screenshot thumbnails, activity rollups, report aggregation" — none of which exists in this codebase yet (no Redis, no BullMQ, no thumbnailing). Standing up a queue just for this one cleanup job was judged out of scope; `ScreenshotsService.deleteExpired()` runs in-process via `@nestjs/schedule`'s `ScheduleModule.forRoot()` (the app's only scheduled job so far), batched at 500 rows per tick so one very large backlog can't hold a tick open indefinitely — it just spreads over subsequent hourly runs. If/when the BullMQ queue described in the tech design actually gets built, this is a natural candidate to move onto it.

- **Screenshot capture library: Electron's own `desktopCapturer`, not a third-party package.** `docs/TECH_DESIGN.md` §5/§10 says "the OS screenshot tool" / `screenshot-desktop` — but Electron ships `desktopCapturer.getSources({ types: ['screen'] })` natively, returning a `NativeImage` that can be resized to the display's real resolution and encoded to JPEG (`.toJPEG(quality)`) with zero extra native dependencies. Given `docs/adr/0011-...`'s packaging pain with native N-API addons (`get-windows`, then `@paymoapp/active-window`), avoiding a second one for screenshots was a deliberate simplification — `desktopCapturer` needs no `asarUnpack`/`node-gyp-build` entry, nothing new in `electron-builder.yml`.

- **Permission: reuses the existing Screen Recording banner, doesn't add a second one.** On macOS, both window-title reading (`docs/adr/0011-...`) and `desktopCapturer` are gated by the same Screen Recording permission (`systemPreferences.getMediaAccessStatus('screen')`). `main.ts`'s `tracking:permissionStatus` banner condition was widened from `windowTrackingEnabled && ...` to `(windowTrackingEnabled || screenshotsEnabled) && ...`, rather than adding a second banner — one macOS permission, one prompt, regardless of which capture feature(s) triggered it.

- **No offline queue for screenshot uploads, matching every other agent network call today.** Same as `AppEventUploader`/timer start-stop (see `desktop/README.md`'s "Known limitations"): a failed capture, failed PUT to Wasabi, or failed metadata POST just drops that screenshot rather than retrying or persisting it locally. `docs/TECH_DESIGN.md`'s SQLite-backed offline queue remains a follow-up for the whole agent, not special-cased here.

## Consequences

- `docs/TECH_DESIGN.md` §2/§6/§10 corrected to say Wasabi (was mistakenly still naming Cloudflare R2 from an earlier draft). `screenshot-desktop`/BullMQ are left as-is — still accurate as *planned* direction, just not what this pass actually built (`desktopCapturer` + in-process `@Cron`, see above); not a stale/forgotten doc issue the way R2 was, so not corrected here.
- `CaptureSettingsGate`'s public contract changed (`onChange` now receives the full `CaptureSettings` object, not a lone boolean) — `desktop/src/main/tests/capture-settings-gate.spec.ts` was rewritten to match; any other future caller of this gate should expect the whole settings shape, not a boolean.
- Screenshot viewing (`GET .../screenshots/mine`, `GET .../memberships/:membershipId/screenshots`) returns presigned, time-limited GET URLs (`SCREENSHOT_URL_TTL_SECONDS`, default 300s) — never a permanent/public link. Only the "mine" gallery has a web console page in this pass (`activities/screenshots`); the membership-scoped endpoint exists (mirroring `AppEventsService.getSummaryForMembership`/`MembershipsController`) but has no admin/manager frontend yet — same gap the app-events summary-for-membership endpoint already had before this ticket, not a new inconsistency.
- Not verified on real macOS hardware (nobody on this project has one — same caveat `docs/adr/0007-...`/`0009-...`/`0011-...` already carry for Screen Recording/idle detection). Linux under Wayland is expected to fail the same way window tracking does (`desktopCapturer` relies on the same underlying screen-capture APIs `get-windows`/`@paymoapp/active-window` couldn't reach under Wayland) — treated as the same "Linux best-effort" gap, not separately re-verified.
