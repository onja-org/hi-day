# URL sessions get a fresh `url_sessions` table (not the orphaned `url_activities`), sync without time-entry clamping for now, and replace the placeholder Activity feed everywhere it appeared

Closes the loop the desktop agent's URL-capture work (Stage A–C, `desktop/src/main/url-capture/`) was built toward but never finished: the client-side capture, local SQLite queue, and `SyncQueue` primitive all existed and were tested, but nothing called them, no backend endpoint existed to receive a sync, and nothing displayed the result. This adds the ingest endpoint, wires the desktop side to actually call it, and displays the result — grouped by URL, with total focused time, a link that opens in a new tab, and (admin/manager only) a delete action — on the member-detail page and, for every user's own account, on the org's Activity page.

## Considered options

- **Reuse the existing `url_activities` table vs. drop and recreate it as `url_sessions`.** An earlier attempt at this feature had already run a migration creating `url_activities` and committed nothing else — no entity, service, or controller for it survives in this tree, and the table holds zero rows. Its shape didn't match the pinned client contract at all (`docs/url-tracking-api.md`'s `UrlSession`) — missing `host`, `path`, `browser`, `private`, `activeMs`, `tzOffsetMin`, `source`, `confidence` entirely, and using an ad-hoc `degradedReason` enum that has no equivalent in the actual client model (`session-types.ts`). Rather than ALTER a stale, empty table into the real shape, the migration drops it and creates `url_sessions` fresh — same reasoning `CreateTimeEntries1788504732663` used for a similarly-abandoned predecessor table.
- **Clamp each synced session's `[startedAt, endedAt]` to the matching running Time entry's window, per `docs/url-tracking-api.md`'s "Joining a UrlSession to a time entry" section.** Not implemented in this pass. That doc explicitly frames the join as "needs a decision from the backend team before reporting queries are built against it" — a flagged-open question, not a settled part of the contract — and nothing this pass actually builds needs it: the display feature groups by URL per Membership, it doesn't attribute time to a specific Time entry or feed a payroll report. Sessions are stored exactly as the client sends them; the clamping/join decision is deferred until a reporting query actually needs it, rather than guessed at now.
- **`id` as the sync endpoint's idempotency key, upserted via TypeORM's `.upsert(rows, ['id'])`.** Matches the contract's explicit requirement ("last write wins on endedAt/activeMs, not first") and needs no hand-written `ON CONFLICT` SQL. `deviceId` is deliberately NOT taken from the synced row — it's always the caller's own `DeviceSessionGuard`-authenticated device, the same reasoning every other device-authenticated write in this codebase already follows (never trust a client-declared identity field when a guard-verified one exists).
- **Grouping "how long a URL was focused in total" at query time (SQL aggregation) vs. in application code.** Chose application code: fetch up to `RAW_SESSION_LIMIT` (1000) raw rows for the target Membership (most-recent first) and group/sum in JS. This mirrors `TimeEntriesService.list`'s own `LIST_LIMIT` precedent — a documented, revisit-later simplification rather than introducing raw SQL aggregation and a harder-to-unit-test query builder chain for a first pass. Private-session rows (`url` stripped to `''` on the client — see `UrlSession`'s own doc comment) are filtered out (`url != ''`); there is nothing meaningful to display or click for one.
- **Who can delete tracked URL history, and what a delete removes.** Confirmed directly: admin/manager only (never a self-service action, even for one's own history), and a delete removes every session for one exact URL for one Membership — not a single visit. `DELETE organisations/:id/url-sessions?membershipId=&url=` is audit-logged (`url_session.deleted_by_url`, with `deletedCount`) since it permanently removes another person's browsing history — the same bar this codebase already holds Time entry edits to.
- **The org's Activity page, the member-detail page's own "Activity" section, and the dashboard's compact preview all showed the same placeholder — a free-text "what are you working on" feed whose own page heading read "Activity Dummy Content".** Confirmed directly: replace it everywhere, not just where first raised. Leaving one of the three showing real tracked-URL data and the other two still showing the abandoned placeholder would be a worse, inconsistent state than finishing the replacement everywhere the same placeholder appeared. The backend `activities` module (entity/service/controller) is left in place — nothing asked for it to be removed, and unlike the frontend components/hooks directly replaced here, it isn't something this change orphans by construction.

## Consequences

`UrlSessionsService` is consumed from two different modules the same way `TimeEntriesService` already is: `UrlSessionsController` (web, `organisations/:id/url-sessions`) for listing/deleting, and `DeviceTrackingController` (device-authenticated, `device/url-sessions/sync`) for ingest — one shared service, never two implementations of the same rule.

The desktop agent now actually uploads: `UrlCaptureService` gained an injectable `upload` (`UploadFn`, defaulting to a no-op so every existing test construction keeps working unmodified) wired into its own `SyncQueue`, and `main.ts` runs `runSync()` on a 30s timer alongside the existing heartbeat, tearing down on logout/quit/unauthorized exactly like the heartbeat and url-capture service already do.

Not built in this pass: the time-entry clamping/join (see above), pagination beyond `RAW_SESSION_LIMIT`, and any change to the backend `activities` feature itself (still reachable, just no longer linked from the frontend nav).
