# Disclosure as a passive, non-blocking notice (supersedes 0014)

Superseded 0014 (the hard consent gate: decline blocked device login/timer entirely, and the backend 403'd capture-ingest routes until a `ConsentRecord` was granted) because the gate was blocking window/screenshot/activity capture from ever starting for organisations where an admin hadn't yet published disclosure text or where a device's user hadn't (or wouldn't) actively click through it. Product decision: capture should start as soon as its own org-level setting is on and a timer is running — the same Hubstaff-style rule everything else already follows — without waiting on a separate per-device acknowledgment step.

**What changed:**
- `DeviceConsentGuard` is removed. `POST /device/app-events`, `/device/activity-samples`, and `/device/screenshots/upload-url` no longer check for a `ConsentRecord` at all — only `DeviceSessionGuard` (a valid device session) applies, same as most other `/device/*` routes.
- The desktop agent's `recomputeSampling()` no longer includes a consent condition — window tracking, screenshots, and activity sampling start based solely on `<capture setting enabled> && <timer running>`.
- The desktop agent no longer shows a full-screen consent gate in place of the login/timer view, and there is no "decline" hard stop. Instead, `GET /device/disclosure`'s response drives a persistent, non-blocking banner shown alongside the normal tracking UI whenever the org has a current published `DisclosureVersion` this device hasn't acknowledged. An "I understand"/"Got it" action calls `POST /device/consent` (unchanged endpoint) purely to record an audit-trail acknowledgment — declining is no longer a UI option, since nothing is gated on the answer either way.
- `DisclosureVersion`/`ConsentRecord` entities, the admin draft/publish UI (`Settings → Consent & disclosure`), and the audit log entries are all unchanged — an org can still author and publish disclosure text, and a device's acknowledgment is still recorded with a timestamp and version reference. Only the enforcement is gone.

**What this means in practice:** disclosure text, if published, is shown to the person using the device, but capture is never conditioned on them seeing or acknowledging it — an org whose admin never bothers to write disclosure text gets exactly the same capture behavior as one that does. Whether that satisfies a given jurisdiction's notice/consent obligations for employee monitoring is now entirely the deploying organisation's own compliance responsibility (e.g. satisfying it through an employment contract clause, a separate onboarding step, or some other out-of-band notice), not something this system enforces or guarantees — see 0014's own "not consent in the legally strict sense" caveat, which now applies even more loosely: this is disclosure infrastructure an org can use, not a compliance mechanism the platform enforces on its behalf.

**Known gap carried forward:** the one-DisclosureVersion-per-region resolution, region fallback, and versioned-immutable-text design from 0014 are all still in place and still correct for what they do — only the "must acknowledge before capturing" behavior is gone.
