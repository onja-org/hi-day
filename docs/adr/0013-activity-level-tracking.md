# Activity level tracking: Hubstaff's own 10-minute/60-segment method, a new `activity_samples` table, and an activity meter on each Screenshots card

`docs/TECH_DESIGN.md` §3/§5 always named `activity_sample` (device_id, level, ts) and `uiohook-napi` as the intended capture mechanism, but neither had been built yet. This ticket implements Hubstaff's own published methodology (https://support.hubstaff.com/how-are-activity-levels-calculated/) end to end: desktop capture, batched ingest, storage, and a summary view — following the exact shape `docs/adr/0010-...` (AppEvent) and `docs/adr/0012-...` (Screenshot) already established for this codebase's other capture pipelines.

## Hubstaff's method, as implemented

Each 10-minute period is divided into sixty 10-second segments. A segment counts as active if it saw any mouse move, click, wheel movement, or key press — Hubstaff's own docs: "a mouse movement or keyboard stroke = active. No keyboard or mouse = inactive," treating all three input kinds as fully equivalent, never weighted. `activePercentage` is `activeSegments / 60 * 100` (equivalently, active seconds ÷ 600 seconds). Only *whether* a segment saw some input is ever recorded — never which key, where the mouse was, or what was typed/clicked — matching Hubstaff's own privacy framing and this codebase's existing AppEvent precedent (app/title only, never raw content).

## Considered options

- **Capture: `uiohook-napi` (global input hook), wrapped defensively.** `ActivitySampler` (`desktop/src/main/activity-sampler.ts`) accumulates input events into a `Set` of active segment indices for the current period, entirely in the main process, and emits one `ActivitySample` per 10-minute boundary — no per-tick sample the way WindowSampler/ScreenshotSampler have, since there's nothing meaningful to report until a period closes. `uiohook-napi` is a native N-API module; per this project's own history with native modules under Electron (`docs/adr/0009-...`'s get-windows ESM issues, and the sqlite-native-binding crash that led to sql.js), it's required lazily inside a `try`/`catch` rather than statically imported, and a load/start failure just disables activity tracking for the session rather than crashing the agent. All input-hook/clock access is dependency-injected so `ActivitySampler` is fully unit-testable without touching uiohook-napi at all.
- **A new org-level toggle, `activityTrackingEnabled`, separate from `windowTrackingEnabled`.** Keyboard/mouse input monitoring is a materially more sensitive capability than reading foreground window titles — an org may reasonably want one without the other — so it gets its own switch on `Organisation.settings` (same jsonb column, same `GET /device/capture-settings` polling mechanism, same running-timer gate as the other two capture settings) rather than being folded into `windowTrackingEnabled`. Defaults to `false`, same "off until an admin opts in" posture as every other capture setting.
- **Storage: `ActivitySample` (`activity_samples` table), one row per 10-minute period.** Same shape as AppEvent/Screenshot: `organisationId`/`membershipId`/`deviceId` FKs, `membershipId` attributed the same way (whoever was signed in on the Device at sample time — never derived from `Device`'s own columns, see CONTEXT.md's Device entry), plus `activePercentage` (smallint 0-100), `periodStart`/`periodEnd` (`timestamptz`). Indexed on `(membershipId, periodStart)`, mirroring AppEvent's own index. Rows are write-once; no raw-event read API beyond the aggregated summary.
- **Ingest: batched, POSTed to `/device/activity-samples`.** `ActivitySamplesModule` has no controller — it exists purely to give `DeviceTrackingModule` access to `ActivitySamplesService.recordBatch` for ingest, same DTO-validated batching shape (`create-activity-samples-batch.dto.ts`) as `AppEventsModule`. `ActivitySampleUploader` (desktop) buffers samples via the existing offline queue and flushes on the queue's normal cadence — no `flushOnEnqueue`, since a sample only arrives once per 10 minutes, there's no batching benefit to chase the way there was for 5-second window samples.
- **No summary/read API — this was tried, then removed.** A first pass added `GET .../activity-samples/summary/mine` and the per-membership equivalent (mirroring AppEvent's own summary routes: a per-day average plus per-period breakdown), with a standalone "Activity level" tab calling it. Once the frontend was reworked to show activity level as a meter on each Screenshots card instead (see below), those routes had no caller left — rather than keep tested-but-unused endpoints around "for later" (unlike AppEvent's per-membership route, which was *never* wired to a page but was the intended primary read path from the start), they were deleted along with the tab/hook/lib/types that called them. `ActivitySamplesService` is ingest-only now (`recordBatch` + its own `getActiveMembership` helper); reintroducing a summary endpoint is a normal follow-up if a future report/chart needs one.
- **Frontend: a meter on each Screenshots card, not a separate tab.** Reworked after seeing Hubstaff's actual UI: activity level and screenshots are shown *together*, one screenshot card per 10-minute period with its own activity meter underneath — closer to what Hubstaff's Activity → Screenshots view actually looks like than two separate tabs would be. `ScreenshotsService.listForMembershipId` queries the day's `ActivitySample`s directly (its own repository, not `ActivitySamplesService`) and attaches whichever one's period contains each screenshot's `capturedAt` (a time-overlap lookup, not a shared foreign key — the two capture loops run independently) via a new `findSampleCovering` helper; `ScreenshotSummaryItem` carries the result (`activePercentage`/`periodStart`/`periodEnd`, all nullable for "no covering sample"). `ScreenshotsPageContent` renders the period label and a new `ActivityMeter` component per card.
- **Meter color: single-hue (brand primary), not a severity ramp.** Hubstaff's own bar colors by severity (green/amber/gray); this frontend's palette is closed to five brand tokens and forbids new colors without explicit sign-off (`frontend/CLAUDE.md`), confirmed with the user rather than assumed. `ActivityMeter` renders ten fixed segments (deciles of `activePercentage`), filled ones `bg-primary` and unfilled ones `bg-primary/15` (an opacity step of the same token, not a new color) — matching the dataviz skill's own meter spec ("the unfilled track is a lighter step of the same ramp") while staying inside the existing palette. Segments are discrete rather than one continuously-sized bar because an arbitrary 0-100 fill width can't be expressed with static Tailwind classes without inline styles or bracketed arbitrary values, both disallowed here.
- **Period length overridable via `DESKTOP_ACTIVITY_PERIOD_MS`, dev/testing only.** The 10-minute period is still the real, Hubstaff-matching default — but waiting 10 minutes to see a single reading made local testing painful, so `ActivitySampler`'s period is configurable via this env var (e.g. `=60000` for 1-minute periods). Segment count stays fixed at 60 regardless (segment duration = period / 60), so `activePercentage` means the same thing at any period length — only how long you wait for a reading changes. No corresponding org-level setting; this is a desktop-process env var, not something the web console can change.
- **`OrganisationSettingsForm` split.** Its capture-toggle fields (already pushing that component past this codebase's ~150-line guideline before this change) were pulled out into `CaptureSettingsFields` when the new `activityTrackingEnabled` toggle was added, rather than letting the file grow further.

## Consequences

No permission-request UI exists yet for whatever OS-level permission `uiohook-napi` needs for a global input hook (macOS Accessibility, most likely) — `WindowSampler`'s macOS Screen Recording flow (`tracking:requestScreenRecordingAccess`/`tracking:openScreenRecordingSettings` in `main.ts`) has no activity-tracking equivalent yet. Today, a missing permission simply means `uiohook-napi` fails to start and activity tracking silently reports nothing (logged to console) rather than surfacing a "Grant Access" prompt the way screenshots do — building that parallel flow is a natural follow-up once this ships and the real permission behavior can be observed on real macOS/Windows hardware (this was implemented and tested in a Linux sandbox with no display attached, so uiohook-napi's runtime behavior there is unverified beyond `require()` succeeding).

A screenshot's card shows "No activity data" whenever no ActivitySample's period covers its `capturedAt` — expected whenever activity tracking is off (screenshots alone don't require it) or the two samplers' periods simply don't align for that moment, not a bug to chase.

**Migration drift, found, fixed, then the fix itself removed:** the dev DB's `activity_samples` table was, for a while, out of sync with the `ActivitySample` entity — it still had `level`/`sampledAt` columns (this ticket's very first draft, matching `docs/TECH_DESIGN.md`'s literal original wording) instead of `activePercentage`/`periodStart`/`periodEnd`. TypeORM tracks applied migrations by name, so once `CreateActivitySamples1789050000000` was marked applied under that earlier draft, rewriting the migration file's contents later (to the shape actually described above) didn't retroactively fix the already-applied table — `migration:run` treated it as done and skipped it. A `FixActivitySamplesColumns` migration was written to patch the live table (a plain drop/add — it was empty at the time) and ran successfully against this one dev DB, but it was **not** kept: `CreateActivitySamples1789050000000` already has the correct final columns in git, so on any *fresh* database the fix migration would immediately fail with "column already exists" — it only ever made sense as a one-off patch for this specific already-drifted DB. Once applied, it (and its `migrations` tracking row) were deleted, leaving only the now-correct `CreateActivitySamples1789050000000` in the migration history. Takeaway for next time: after materially changing an entity whose migration has *any* chance of already being applied somewhere, diff the live table's actual columns, not just row counts or `migration:show`'s applied/pending status — and if a patch migration is needed to fix drift, treat it as a throwaway operational fix, not a permanent part of the migration chain, once the underlying (now-correct) migration is what every fresh install will actually run.
